Inside the development work.

THE BOSS is a personal, non-commercial software project for document review and a traceable local ledger. This page documents the application and recovery engineering at a level that can be shared publicly. The implementation, private workspaces and detailed internal receipts are not published.

Application components

Workspace ledger
A workspace-specific SQLite database holds records associated with that workspace. Recovery must preserve the intended workspace identity and avoid mixing records between workspaces.
Document storage
Encrypted source originals support later review and authenticity checks. Recovering database rows alone is insufficient if their source documents cannot also be authenticated.
Checkpoint evidence
Checkpoint ledgers and consistency checks help establish whether the supported record sets were preserved through export and restore.
Portable export and isolated restore
Compatible Python components capture a supported package and validate it into a new destination. The selected toolchain must match the source's physical schema; a successful synthetic test alone does not establish compatibility with another workspace.

A concrete compatibility problem

During recovery preparation, an exporter refused a workspace because the actual physical schema did not match its expected fingerprint. The response was to identify the mismatch and validate isolated, unchanged toolchains against their matching schemas. The source database was not migrated to make an export succeed, and fingerprint validation was not bypassed.

This distinction matters in software development: a recorded schema revision and a database's actual table structure must agree with the exporter's expectations. Selecting a toolchain by name or by a successful test against a different fixture is not enough.

How recovery testing is structured

  1. Build a fictional fixture. Use synthetic records, synthetic documents and disposable credentials, isolated from real workspaces.
  2. Establish the starting identity. Record the toolchain version, expected physical schema and fixture workspace identity before export.
  3. Run the supported export. Use the toolchain's existing export path and validate the completed package.
  4. Restore to a fresh destination. Exercise the corresponding restore path separately from the fixture source.
  5. Compare the supported data. Check schema identity, database integrity, supported financial rows, checkpoint ledgers and source-document authentication. Count comparisons alone are not a substitute for record consistency.
  6. Record the limits. A same-host isolated test is useful development evidence, but it is not a clean-OS or replacement-hardware rehearsal.

Recorded development milestones

  • Synthetic export and restore: on 17 October 2026, two separately pinned recovery toolchains completed their matching synthetic validation. Each harness reported nine checks and seven authenticated members, with no private sources accessed. These are summaries of existing local test receipts, not a new public test run or a release certification.
  • Portable environment preparation: a recovery kit packages source and dependency wheels with SHA-256 manifests. It supports rebuilding an environment rather than treating an existing virtual environment as a portable installation.
  • Independent backup readback: encrypted repository data was downloaded and authenticated with the local backup drive disconnected. This validates the captured repository and selected recovery-kit files; it does not establish full source coverage or application startup on new hardware.

Remaining development work

  • Broader supported source coverage and compatibility validation for workspace variants.
  • Fresh-profile authorisation recovery and a complete replacement-PC exercise.

No application release, hosted financial service or public demo containing private records is offered here. Development status and test limitations are stated explicitly rather than claiming production readiness.

Where Google Drive, restic and rclone fit

They form a storage and transport layer around the project's recovery work. Restic supplies encrypted snapshots, rclone supplies the Drive connection, and Google Drive stores the encrypted repository. They are third-party tools, not software authored by THE BOSS. The workspace ledger, physical-schema compatibility, portable export/restore validation and dependency packaging are the project-specific engineering concerns described above.

The site's privacy policy explains the owner's Google Drive connection. It does not grant access to the application, records or backups.
